# Phase 0 spike — 2026-09-30

Questions from ADR 0008 and 0011: do both models train in 8GB at resume-sized inputs,
does the pinned toolchain support them end to end, and can raw `/completion` take images
with train/inference parity?

**Answer: yes to all three.** Details below. Scripts: `scripts/spike/`.

## Model facts

| | Qwen3.5-4B | Qwen3-VL-4B-Instruct |
|---|---|---|
| HF class | `Qwen3_5ForConditionalGeneration` — **natively multimodal** | `Qwen3VLForConditionalGeneration` |
| Text layers | 32: 24 Gated DeltaNet (linear) + 8 full attention | 36, full attention |
| Vocab | 248,320 | 151,936 |
| Vision tower | 24 layers, patch 16, merge 2 | identical shape |
| 4-bit checkpoint | none; quantised at load from 9.3GB bf16 | `unsloth/…-unsloth-bnb-4bit` (4.3GB) |
| GPU after 4-bit load | 3,192 MiB | 4,111 MiB |

Qwen3.5's linear-attention layers ran on the **torch fallback**: `flash-linear-attention`
and `causal-conv1d` are not installed. It was still the faster model; installing them is
an optional speed-up, not a requirement.

## Training VRAM (`vram_probe.py`)

QLoRA r=16, language layers only, Unsloth gradient checkpointing (offloads activations
to CPU), loss on a 701-token target, adamw_8bit, batch 1. Peak = whole device per
`nvidia-smi`, sampled every 200 ms. Step time = steady state (first step includes
kernel compilation: 12–75 s).

| Model | Input | Seq len | Peak (smi) | Step |
|---|---|---|---|---|
| Qwen3.5-4B | text, 3k tokens | 3,721 | **5,165 MiB** | 4.0 s |
| Qwen3.5-4B | text, 6k tokens | 6,721 | 5,883 MiB | 8.2 s |
| Qwen3.5-4B | 1 page 1000×1400 | 2,086 | 4,577 MiB | 2.3 s |
| Qwen3.5-4B | 2 pages 1000×1400 | 3,452 | **4,977 MiB** | 3.8 s |
| Qwen3.5-4B | 2 pages 1240×1754 | 5,014 | 5,566 MiB | 6.0 s |
| Qwen3-VL-4B | text, 3k tokens | 3,717 | 6,208 MiB | 5.7 s |
| Qwen3-VL-4B | 1 page 1000×1400 | 2,083 | 5,638 MiB | 2.8 s |
| Qwen3-VL-4B | 2 pages 1000×1400 | 3,449 | 6,172 MiB | 5.3 s |
| Qwen3-VL-4B | 2 pages 1240×1754 | 5,011 | 6,774 MiB | 9.8 s |

A 1000×1400 page is ~1.36k vision tokens (32 px per token after the 2×2 merge). Every
configuration fits; Qwen3.5-4B leaves ≥1.7GB of margin even at 6.7k tokens, where the
persona repo's Qwen3-8B had ~0.5GB at 1.5k.

Caveat: a manual loop, not TRL's `SFTTrainer`. Re-check the peak on the first real run.

## llama.cpp export and serving (Qwen3.5-4B)

- `convert_hf_to_gguf.py` → f16 (8.7GB) and `--mmproj` → f16 projector (672MB): OK.
  The HF chat template's Jinja is embedded; `raise_exception` lines in the log are the
  template source, not errors.
- `llama-quantize` → Q4_K_M: **2.8GB**. Unused MTP (`nextn`) tensors are ignored on load.
- `llama-server -ngl 99 -c 8192 --mmproj`: **~4.4GB** VRAM while generating with an image.
- Qwen3-VL conversion is registered in the same converter (`conversion/qwen3vl.py`);
  not run end to end in this spike.

## Raw `/completion` with images (ADR 0011)

Works. The request is `{"prompt": {"prompt_string": …, "multimodal_data": [base64]}}`.

- The prompt string must contain the server's **media marker** where each image goes.
  In this llama.cpp the marker is **randomised per server run** (anti prompt-injection):
  read it from `GET /props` → `media_marker`, or pin it with `LLAMA_MEDIA_MARKER`.
  The documented `<__media__>` is rejected ("number of media markers (0) does not match").
- mtmd inserts `<|vision_start|>`/`<|vision_end|>` itself, so the whole HF image block
  `<|vision_start|><|image_pad|><|vision_end|>` becomes one marker.
  `cvx.prompt.to_server_prompt` does this.
- **Parity measured:** HF processor input = 1,465 tokens (image grid 1×88×62); server
  `prompt_n` = 1,465. Text path: HF and `/tokenize` produce identical ids (263 tokens).

## Base-model behaviour (a warning for the eval design)

On a clean, single-column toy resume, **base** Qwen3.5-4B:

- free decoding: well-formed JSON with its own keys (`localizacao`, `data_inicio`,
  `"atual"`) → `schema_violation`, from both text and image;
- with `json_schema` grammar, from the **image**: every field correct.

So on easy layouts the base model plus grammar is already strong. The fine-tune has to
earn its keep on hard layouts (two columns, tables, sidebars, scanned noise), on
format-without-grammar, and on the real test set. The synthetic test split must be
designed to be hard, or the A/B will show nothing.
